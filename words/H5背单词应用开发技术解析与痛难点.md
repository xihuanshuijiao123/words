# 手把手带你读懂一个「移动端背单词 H5 应用」的开发过程与技术难点

## 一、先弄清楚：我们到底在做什么

如果你是一名大学生，现在想要做一个「手机上背英语单词」的应用，你会发现市面上已经有很多现成的 App 了。但如果你想亲自写一个，或者想弄明白别人写好的项目是怎么跑起来的，那么这篇文章就是为你准备的。

我们要讲的项目，本质上是一个 **H5 网页应用**。

什么叫 H5？简单说，就是用「网页技术」做出来的、能在手机浏览器里打开的应用。它不需要下载安装，只要有一个网址，用微信、手机浏览器点开就能用。它的好处是「一次开发，处处运行」，不管是 iPhone 还是安卓手机，都能直接打开。

这个应用解决的需求很朴素：**让学生像翻卡片一样背单词**。

你打开首页，能看到一本一本的「单词书」——比如人教版 PEP 三年级上册。点进一本书，就进入「学习页」，屏幕上会出现一张单词卡片，正面是单词 `ruler`、音标 `/ˈruːlə/`、还有发音按钮。点「下一个」，就切换到下一个单词。如果你已经学过，它会记住你学到第几个，下次打开还能接着学。点卡片还能进「详情页」，看到这个词的完整释义、例句、短语、同根词和记忆技巧。

一句话总结：**这是一个「单词书浏览 + 卡片式背单词 + 学习进度记忆」的移动端网页应用。**

---

## 二、这个项目的大脑：技术选型是怎么定的

做任何项目，第一步都是选工具。这个项目用的核心是这几样：

- **Next.js**：这是一个非常流行的前端框架，它解决了一个大问题——**我们写的网页既有 HTML 页面，又需要处理数据请求，还可能需要登录校验**。Next.js 把这些事情整合在一起，还能自动做路由（一个网址对应一个页面）。
- **App Router**：这是 Next.js 比较新的路由方式。它的特点是「文件夹就是路由」，比如 `app/learn/[bookId]/page.tsx` 这个文件，就对应一个网址 `/learn/某个书号`。这种「见文件见路由」的方式对新手极其友好，不用去翻配置文件。
- **TypeScript**：其实是 JavaScript 加了「类型」。相当于在写代码时告诉编译器「这个变量必须是数字、那个必须是字符串」，这样很多低级错误在写代码的时候就被拦住了。
- **Tailwind CSS**：一种写样式的方式，允许你在 HTML 标签上直接写 class 来控制界面，不用单独建一堆 CSS 文件。
- **shadcn/ui**：一套现成的界面组件（按钮、卡片、弹框、输入框等），拿来就能用，省去从零手写 UI 的麻烦。
- **Drizzle ORM + PostgreSQL**：这是「数据库」部分。Drizzle 是一种叫 ORM（对象关系映射）的工具，它让你能用写 TypeScript 代码的方式去操作数据库，而不是手写一长串 SQL 语句。PostgreSQL 则是实际存放数据的数据库。

看起来选择很多，但核心思路只有一条：**尽可能写更少的「重复劳动」，把精力放在业务逻辑上。** 这套组合是业界公认的「好上手、够用、不容易出错」的搭配。

## 三、最难啃的骨头：数据模型与那个「套娃」JSON

如果你要做一个背单词应用，第一件事就是要想清楚：**一个单词的数据长什么样？**

这里就遇到了这个项目最大的难点——**数据结构的嵌套极深**。

一个单词在数据库里不是简单的一行「单词 = 尺子」，而是一个像「俄罗斯套娃」一样层层包裹的 JSON 对象。我们看真实的数据长什么样：

```json
{
  "wordRank": 1,
  "headWord": "ruler",
  "content": {
    "word": {
      "wordHead": "ruler",
      "wordId": "PEPXiaoXue3_1_1",
      "content": {
        "sentence": {
          "sentences": [
            { "sContent": "a 12-inch ruler", "sCn": "一把12英寸的尺子" }
          ]
        },
        "usphone": "'rulɚ",
        "ukphone": "'ruːlə",
        "ukspeech": "ruler&type=1",
        "usspeech": "ruler&type=2",
        "trans": [{ "tranCn": "尺子", "tranOther": "a long flat ..." }],
        "phrase": {
          "phrases": [{ "pContent": "pencil case", "pCn": "文具盒" }]
        },
        "syno": {
          "synos": [
            { "pos": "n", "tran": "...", "hwds": [{ "w": "governor" }] }
          ]
        },
        "relWord": {
          "rels": [
            { "pos": "adj", "words": [{ "hwd": "ruling", "tran": "..." }] }
          ]
        },
        "remMethod": { "val": "没有规矩(rule)..." }
      }
    }
  },
  "bookId": "PEPXiaoXue3_1"
}
```

新手看到这里往往会崩溃：怎么这么深？取一个「中文释义」，要写好几层：`content.word.content.trans[0].tranCn`。

这里有两类让人头大的问题：

**1. 字段名「上有政策、下有对策」——命名不一致。**

同一个项目里，`words` 表的列名是「驼峰写法」，比如 `bookId`、`wordRank`；而 `books` 表却用「下划线写法」，比如 `book_id`、`word_count`。为什么？因为这两张表来自不同的来源，一个是从已有的后台系统迁移过来的，一个是新设计的。这就导致写代码时，查询这两张表必须非常小心，该用 `"wordRank"` 的地方绝对不能用 `word_rank`，否则数据库报错。

**2. `content` 字段是 `json` 而不是 `jsonb`。**

在数据库里，JSON 有两种存储方式：`json` 和 `jsonb`。前者只是「原样存字符串」，后者会「解析成结构化格式」，查询更快、支持索引。这个项目因为要和已有后台共用数据，`content` 用的恰恰是查询更慢的 `json`。所以取某个词条的时候，必须用 PostgreSQL 的特殊语法 `content #>> '{word,wordId}'`（意思是「沿着路径取一个值」），而不能直接用常见的点号取法。

**解决办法**：用 TypeScript 的类型（`type WordContent = { word?: { wordHead: string; wordId: string; content: {...} } }`）把这些结构「固化」下来。这样写代码时，编译器会直接告诉你「你取的这个字段可能不存在，要不要加个可选判断？」，从而把运行时容易崩的坑提前到写代码时暴露出来。

## 四、登录到底是怎么实现的？Cookie 与密码那些事

背单词应用需要「记住你是谁」，否则怎么知道你的学习进度？所以必须有登录。

但这个项目在登录上踩了不少坑，核心是两点：**密码怎么存**、**登录状态怎么记**。

**密码绝不能明文存储。** 这个项目用了两种加密方案，其实都可以，只是在不同项目里用了不同的库：

- 一个是 `bcrypt-ts`，专门做密码哈希的库。哈希的意思是：把密码经过一种单向算法变成一串乱码，**存进数据库的是这串乱码，而不是密码本身**。登录时，再把用户输入的密码做同样的哈希，和数据库里的比对。比对用的是 `compare` 方法。
- 另一个是 Node.js 自带的 `crypto.scrypt`。原理一样，只是不依赖第三方包。

**登录状态怎么保持？** 最经典的做法是 **Cookie（浏览器的「凭证小纸条」）**。登录成功后，服务器生成一个不可猜测的 `token`，存到数据库的会话表里，同时把这个 token 塞进浏览器的 Cookie，并设置 `HttpOnly`（意思是「网页里的 JS 代码读不到它」，能有效防止别人偷走）。

下次请求时，浏览器会自动带上这个 Cookie，服务器一看就知道「你是谁」，而且这个 token 有过期时间（这个项目设的是 **7 天**，7 天后自动失效，逼你重新登录，保证安全）。

**这个项目的一个特别之处**：它其实有两个数据来源体系。`nextjs-typescript-starter` 本身是一个基于 NextAuth 5.0（一个登录授权框架的 beta 版本）的模板，用 `Credentials` 方式（邮箱 + 密码）做登录。但项目真正想复用的是旁边 `words-admin` 后台那一套「Cookie + 会话表」的方案，因为两套系统共享同一份数据库的 `admin_sessions` 表。这种「同一份用户数据、两套登录实现」的取舍，就是真实项目里经常遇到的「复用 vs 独立」的选择题。

## 五、最聪明的部分：学习进度与「接着上次学」

背单词应用最好玩、也最容易出 bug 的地方，是**记录进度**。

试想：你学到一本单词书的第 3 个词了，关掉应用。第二天打开，它得知道「你很厉害，已经学到第 3 个了，下次从第 4 个开始」。怎么办？

这个项目设计了两个「层次」的进度：

**第一层：书级进度（`study_progress` 表）。** 记录「用户 + 一本书」这一条进度。里面存 `last_rank`（上次学到第几个词）、`done_count`（已经看过几个词）。而且加了约束：**同一个用户同一本书，只能有一条进度记录**。这就保证不会重复堆数据。

**第二层：词级掌握（`word_records` 表）。** 记录「用户 + 单个单词」的掌握情况，状态有 `new`（没学）、`learning`（学习中）、`mastered`（已掌握）。这一层是为以后做「智能复习」打基础的。

**这里有个精妙的点：`续学锚点`。** 下次进入学习页时，程序不是随便从第 1 个词开始，而是计算 `nextRank = lastRank + 1`（也就是上次学到的下一个）。但如果用户上次已经学完一整本书，`last_rank + 1` 就超出范围了，所以代码里必须加一个「防越界」的判断：`Math.min(start, Math.max(0, words.length - 1))`。这个细节非常容易出错，稍不留神就会数组越界，页面直接崩掉。

**再一个精妙的点是：一次点击，要同时更新两张表。** 你点「下一个」，程序要同时更新「书级进度」和「词级掌握」。这两件事必须「要么都成功、要么都失败」，否则会出现「书说学到第 4 个了，但第 4 个词其实没记录」这种数据对不上的 bug。解决方法是使用数据库的 **事务（transaction）**，把两步绑成一个整体。更新时还用 `onConflict`（冲突时更新）的 upsert 写法，保证「有记录就更新、没记录就新增」。

## 六、前端页面的组织方式：路由组与底部 Tab

有了数据和登录，接下来是「界面怎么拼」。

这个应用是移动端的，所以最典型的就是**底部导航栏**（两个 Tab：首页、我的）。这里 Next.js 的 App Router 提供了一个非常聪明的约定——**路由组**。

你可以用带括号的文件夹，比如 `app/(main)/`，把「希望共享同一套布局（比如都有一个底部导航栏）」的页面放进去。这样 `(main)` 下面的所有页面都会自动套上那个布局。而学习页、详情页这类「全屏沉浸式、不想要底部导航栏」的页面，就放在路由组外面，这样它们就不受底部导航栏的影响。

这个约定非常实用，但也需要理解「括号只是分组、不会出现在网址里」这个关键点，很多新手第一次会以为网址会带 `(main)`。

## 七、真实的「踩坑」记录：新手容易卡住的几个地方

写代码不只是把逻辑写对，很多时候是跟环境、工具、网络作斗争。这里记录几个真实发生过的坑：

**1. 构建工具的问题。** Next.js 默认用 Turbopack 这个工具加速构建，但有时候它在某些电脑上会报「原生绑定缺失」。解决办法很简单：改用传统的 Webpack 构建（在脚本里加 `--webpack`）。这种「换个构建器就解决了」的问题，通常是环境差异导致的，心态要稳。

**2. 数据库连不上，往往不是密码错。** 很多时候你会遇到一个特别诡异的问题：明明密码是对的，却连不上数据库。这个项目就遇到过：云数据库给了一个「直连地址」，但这个地址只有 IPv6（新一代网络地址）。如果你的网络不支持 IPv6，就会一直报 `ENOTFOUND`（找不到地址）。解决办法是改用「Session pooler」连接串，并且通过脚本自动扫描各个区域，确定正确的数据库区域（这里是新加坡 `ap-southeast-1`）。这告诉我们：**连不上库时，先别急着怀疑密码，先检查地址通不通、网络协议对不对。**

**3. 数据库证书报错。** 连接串里如果写了 `sslmode=require`，某些情况下会触发「证书校验」，报 `self-signed certificate in certificate chain`。解决办法是在连接配置里明确写 `ssl: { rejectUnauthorized: false }`（跳过证书校验），并把连接串里的 `sslmode=require` 去掉。

**4. 环境变量加载问题。** 像 `drizzle-kit` 这样的数据库迁移工具，默认不会自动去读 Next.js 的 `.env` 文件，导致程序里读不到 `DATABASE_URL`。解决办法是写一段小代码手动读取 `.env`，把里面的变量注入到环境里。

**5. TypeScript 的「这文件不是模块」报错。** 有时候一个文件只导出了类型或是空文件，会报 `File '...ts' is not a module`。在文件末尾加一个 `export {}` 就能解决。这类报错往往看起来很吓人，其实一两行就能修好。

## 八、把这些串起来：一个完整的学习流程

现在我们把所有知识串一遍，你就能看懂整个流程了：

1. 用户打开首页 `/`，页面从数据库拉取所有单词书，渲染出一排卡片。因为还没登录，看不到「最近学习」。
2. 用户点了一本书，系统发现没登录，就切换到「我的」Tab，并自动弹出「登录/注册」弹窗。
3. 用户注册后，密码被哈希存进 `users` 表，生成一个 7 天有效的会话 token 存进 Cookie。
4. 用户回到那本书的学习页 `/learn/书号`。这时系统去查 `study_progress`，发现这本书之前没学过，就返回「从第 1 个词开始」。
5. 学习页加载这本书的所有词条（按 `wordRank` 从小到大排好），只取卡片需要的那几个字段（单词、音标、中释、一条例句、发音参数）。
6. 用户点「下一个」，程序一方面往前翻卡片，另一方面调用接口，用事务把「书级进度」和「词级掌握」两张表一起更新。这样下次进来就能续学了。
7. 用户点卡片进入详情页 `/word/书号/词号`，渲染这个词的全部信息（完整释义、所有例句、短语、同根词、记忆技巧）。

## 九、写在最后：从这项目里能学到什么

作为大学生，看这样一个项目，真正值得学的不只是「怎么写代码」，而是**怎么把一个模糊的想法，拆成一个个清晰的模块**：

- **需求先行**：先写需求文档（proposal），搞清楚「要做什么、不做什么」。
- **技术设计**：再写设计文档（design），想清楚数据库表、接口、页面结构、业务规则。
- **数据结构是骨架**：背单词应用最核心的，就是那个嵌套的 JSON 词条和两张进度表。数据设计想清楚了，后面就顺了。
- **安全的红线**：密码要哈希、登录要靠会话 token、敏感 Cookie 要 `HttpOnly`。
- **边界情况**：数组越界、数据为空、网络异常、学到最后一词……这些都是新手最容易忽略、却最影响体验的地方。

技术选型不是越花哨越好，**够用、好维护、团队都看得懂**才是关键。而这个项目里的很多「痛难点」，恰恰是真实工程里最常见的问题——嵌套数据、命名不一致、连接配置、进度记忆。你能把一个词条 JSON 看懂，把 `last_rank + 1` 的续学逻辑想明白，把「为什么密码要哈希」说清楚，就已经超过绝大多数刚入门的人了。

希望这篇文章能帮你真正「看懂」一个背单词应用背后的门道，也愿你在动手写自己的项目时，少走一些弯路。
